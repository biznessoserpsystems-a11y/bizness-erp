# Bizness-OS

A modular ERP system. This build includes the following fully working modules:

- **Module 01 — Authentication & Security**: registration, login with account lockout, JWT access/refresh tokens, MFA (TOTP), password reset, roles & permissions (RBAC), audit trail, activity logs.
- **Module 15 — System Administration**: company profile, multi-branch management, financial years & fiscal periods (with auto-generated monthly periods), currencies.
- **Module 05 — Inventory & Warehouse Management**: product master (with categories/brands/units of measure), multi-warehouse stock, stock in/out, warehouse-to-warehouse transfers, stock adjustments, damaged goods logging, batch/lot tracking with FIFO consumption, expiry tracking, reorder-level alerts, weighted-average inventory valuation, and a full audit-grade stock movement ledger.
- **Module 07 — Sales & Distribution**: a lightweight customer entity, quotations → sales orders → delivery notes → invoices → customer payments, plus sales returns with auto-generated credit notes and recurring invoice templates that auto-generate real invoices on a schedule. Delivery notes draw down real warehouse stock through the Module 05 ledger; invoices compute due dates from customer payment terms; payments support partial/split allocation across multiple invoices; VAT-style tax and discounts are calculated per line. Reports cover sales summary, receivables aging, and a sales register — the latter two exportable to Excel/PDF/Word (see "How report export works" below).
- **Module 08 — Procurement & Purchasing**: the buy-side mirror of Sales. A supplier entity, purchase requisitions → RFQs (with supplier quotations) → purchase orders → goods received notes → purchase invoices → supplier payments, plus purchase returns with debit notes and procurement contracts. Goods received notes increase real warehouse stock through the Module 05 ledger (with batch/expiry capture); purchase invoices compute due dates from supplier payment terms; supplier payments support partial/split allocation across bills. Like Sales, it **auto-posts** to the ledger: a purchase invoice books Dr Inventory / Dr Input VAT / Cr Accounts Payable, and a supplier payment books Dr Accounts Payable / Cr Cash — keeping the trial balance in balance. Reports cover a purchase summary and payables aging.
- **Module 10 — Accounting & Finance**: a full double-entry general ledger. Standard Ghanaian SME chart of accounts (auto-seeded on company registration), manual journal entries with balance enforcement and reversal, trial balance, account ledgers with running balances, income statement / balance sheet / financial ratios, bank accounts with manual reconciliation, petty cash accounts and vouchers, budgets with budget-vs-actual variance, opening balances, and month-end / year-end closing. Crucially, the Sales, Procurement, and Payroll modules **auto-post** to the ledger: a sales invoice books Dr Accounts Receivable / Cr Sales Revenue / Cr VAT Payable; a customer receipt books Dr Cash / Cr AR (with unallocated cash going to Customer Advances); a sales return reverses the revenue side; a purchase invoice books Dr Inventory / Dr Input VAT / Cr Accounts Payable; a supplier payment books Dr AP / Cr Cash; and a processed payroll run books Dr Salaries & Wages + Dr SSNIT Employer Contribution / Cr PAYE Payable + Cr SSNIT Payable + Cr Net Salaries Payable. Every posting keeps the trial balance in balance.
- **Module 12 — HR & Payroll**: employee records (distinct from system users — not every employee needs a login, and not every user is on payroll), leave management with configurable leave types and an approval workflow, and monthly payroll runs that generate payslips per active employee with Ghana SSNIT and PAYE income tax computed automatically. Statutory rates are **configurable per company** rather than hardcoded — the SSNIT employee/employer rates, the annual insurable ceiling, and the full PAYE band table are all editable under **HR & Payroll → Statutory Settings**, so you can update them yourself when the GRA revises the schedule. Payroll runs follow a draft → processed → paid lifecycle and **auto-post to the general ledger** (see below). Terminating an employee is a one-click action that sets their status and termination date. Leave approvals that fall within the current date window automatically flip the employee's status to `on_leave`.
- **Module 02 — CRM**: a pre-customer lead pipeline with six stages (new → contacted → qualified → proposal → won → lost), assignable to a sales rep. Leads carry estimated value and expected close date. A one-click **Convert to Customer** action creates a real `customers` row (wired into the Sales module), migrates the lead's contacts, and links the two records. Named **contacts** (first/last name, title, email, phone, primary flag) can be attached to both leads and customers. A shared **activity log** (calls, emails, meetings, notes, and follow-up tasks with due dates) is attached to leads and customers alike — overdue follow-up tasks are automatically surfaced as notifications by the background scanner.
- **Module 13 — Communications**: an in-app notification system with a bell in the top bar and unread counts, company-wide announcements, and a communication log that records calls, emails, meetings, and notes against customers, suppliers, and leads. Background scanners raise notifications for business events (low stock, overdue invoices, and similar), so the system surfaces things that need attention rather than waiting to be asked.
- **Module 04 — Supplier Management**: promotes the minimal supplier entity into a full vendor-management module. Supplier groups for categorisation, multiple named contacts per supplier, a supplier-specific communication log, and a performance scorecard computing on-time delivery rate, average lead time, and invoiced value from real purchase-order and goods-receipt history. Each supplier gets a workspace with ledger, contacts, communications, and scorecard tabs.
- **Module 06 — Asset Management**: a fixed asset register with categories that carry their own GL account wiring (asset, accumulated depreciation, and depreciation expense). Supports straight-line and reducing-balance depreciation via a periodic depreciation run, plus revaluation, impairment, and disposal — each posting its own journal entry, with gains and losses routed to dedicated accounts. Reports cover the asset register, depreciation history, and disposals.

Built with **React (Vite) + Node/Express + PostgreSQL**, with Ghana-specific fields (TIN, GRA, regions, GHS currency, 15% default VAT, SSNIT, PAYE) baked in.

Approval Workflows, Tasks & Calendar, Attachments, and the full HR suite (Employee Management, Shifts & Attendance, Recruitment, Onboarding, Learning & Development, Performance Management, Employee Self-Service, HR Compliance) and Asset Assignment/Closeout are also built — see each migration file's header comment (`013` through `025`) for specifics. Multi-currency support (`026_multi_currency.sql`) is described below. Every module in the sidebar is enabled; there are no remaining "Coming soon" placeholders. Note: the `customers` and `suppliers` tables started as minimal subsets built to unblock Sales and Procurement, but Supplier Management (supplier groups, performance scoring, contacts) has since been built out on top of them.

### How the inventory ledger works

Every stock change — receiving goods, issuing them, transferring between warehouses, adjusting counts, writing off damage, dispatching a sales delivery, or receiving a sales return — is recorded as an immutable row in `stock_movements`. The `stock_levels` table is a materialized balance kept in sync by the application layer so reports stay fast; if the two ever disagree, the movement ledger is the source of truth.

- **Costing**: non-batch products use a moving weighted-average cost, recalculated on every receipt. Batch-tracked products carry their own `unit_cost` per batch instead.
- **Batch/lot + expiry**: when a product is marked batch-tracked, stock-outs (including sales deliveries) default to FIFO by soonest-expiry-first (falling back to received date), automatically splitting across multiple batches if needed. A specific batch can also be chosen manually.
- Physical inventory counts snapshot one line per batch for batch-tracked products (and one aggregate line for non-batch products). Completing a count reconciles each batch's `quantity_remaining` individually, then recomputes the product's aggregate `stock_levels` row from its batches — the same recalculation any other receipt/issue triggers, so a completed count can't be silently overwritten by the next stock movement.

### How the sales chain works

Quotation → Sales Order → Delivery Note → Invoice is a loose pipeline, not a rigid one: a sales order can be created standalone (no quotation), an invoice can be created standalone (no sales order), and partial deliveries/partial invoicing against the same order are both supported (each order line tracks `delivered_quantity` and `invoiced_quantity` independently). Payments support partial allocation — a single receipt can be split across several invoices, or left partially unallocated as credit on account. Sales returns immediately restock the warehouse and auto-generate an open credit note, which can then be applied to any of that customer's outstanding invoices. Customer credit limits are enforced as a soft warning on invoice creation, not a hard block — the response includes a `creditWarning` field the frontend surfaces, but the invoice still goes through.

### How the accounting engine works

The double-entry core lives in `server/src/services/accountingService.js`. Every posting goes through `postJournalEntry`, which refuses to write anything unless total debits equal total credits, so the ledger can never go out of balance. Account "normal balances" (asset/expense = debit; liability/equity/revenue = credit) drive how balances are computed for the trial balance, ledgers, and statements.

- **GL mappings**: the Sales module doesn't hardcode account IDs. Instead it looks up semantic roles — `accounts_receivable`, `sales_revenue`, `vat_payable`, `cash_default`, `customer_advances`, etc. — in the `gl_account_mappings` table. This means auto-posting is *optional and safe*: if a company hasn't set up its chart of accounts, `hasAllMappings` returns false and the sale/payment still succeeds, just without a journal entry. New companies get the standard chart and mappings seeded automatically at registration; existing companies can seed them anytime via **Accounting → Chart of Accounts → Set up defaults** (or `POST /api/accounting/setup-defaults`).
- **Fiscal period locking**: postings look up the fiscal period covering their date. If that period is `closed` or `locked`, the posting is rejected — but if no financial year has been set up yet, posting is allowed (so you're not blocked before configuring System Admin). Month-end close sets a single period to `closed`; year-end close zeroes all revenue/expense accounts into Retained Earnings and locks the whole year.
- **Financial statements**: the income statement is a period flow (movement between two dates); the balance sheet layers opening balances + all journal movements up to the as-of date, and folds current-year earnings into equity so it balances. Opening balances are entered once for a company's first year on the system; subsequent years roll forward through year-end closing rather than a fresh opening-balance entry.
- **COGS**: a delivery note posts Dr Cost of Goods Sold / Cr Inventory at the actual FIFO/weighted-average cost the stock ledger recorded for the goods that physically left the warehouse (`referenceType: 'delivery_note'`). A sales return reverses both sides of the original sale: the revenue/AR/VAT entry as before, plus a Dr Inventory / Cr COGS reversal at the same cost basis used to restock the goods (the product's current weighted-average cost — **not** the price the customer was charged, which would otherwise corrupt the inventory valuation).
- **Bank reconciliation**: `POST /api/bank-accounts/:id/auto-reconcile` matches unreconciled statement lines to unmatched GL lines on that account, one-to-one, by exact amount and closest date. Manual matching (`PATCH /bank-statement-lines/:id/reconcile`) is still available for anything the auto-matcher leaves behind or gets wrong.

### How financial statements follow IFRS (IAS 1)

Both primary statements were restructured to match IAS 1's presentation requirements rather than a flat, undifferentiated layout — `030_ifrs_alignment.sql` is what made this possible, since it backfills the two account subtypes and one account the base chart was missing.

- **Statement of Financial Position** (the balance sheet, per IAS 1.60-76): assets and liabilities are each split into **non-current** and **current**, using the `account_subtype` the chart of accounts already carried (`fixed_asset` → non-current; anything else → current for assets, `long_term_liability` → non-current; anything else → current for liabilities). The base chart shipped with every liability marked `current_liability`, so there was nothing to classify as non-current — `030_ifrs_alignment.sql` backfills a `Long-term Loans Payable` (2500) account into every existing company (and the default seed for new ones) so the split has somewhere real to put a bank loan or finance lease. Presentation order is non-current first, current second (the common IFRS illustrative ordering — ascending liquidity — though IAS 1 itself doesn't mandate an order, only that the split exist).
- **Statement of Profit or Loss** (the income statement, classified **by function** per IAS 1.99-105 — cost of sales, not raw expense categories): restructured into Revenue → Cost of Sales → **Gross Profit** → Operating Expenses → **Operating Profit** → Finance Costs → **Profit Before Tax** → Income Tax Expense → **Profit for the Period**. Finance costs (IAS 1.82(b)) and income tax expense (IAS 1.82(d)) must each be their own line, not folded into "operating expenses" — the base chart had no accounts for either, so `030_ifrs_alignment.sql` backfills `Finance Costs` (6800, subtype `finance_cost`) and `Income Tax Expense` (6950, subtype `tax_expense`) into every existing company and the default seed.
- **Backward compatibility**: `GET /financial-statements/balance-sheet` still returns flat `assets`/`liabilities` arrays alongside the new `nonCurrentAssets`/`currentAssets`/`nonCurrentLiabilities`/`currentLiabilities` ones — `Dashboard.jsx` and `AccountingWorkspace.jsx` both filter the flat array for bank-account rows to compute a cash total, and didn't need to change.
- **What this doesn't cover**: the extensive notes/disclosures IFRS requires around accounting policies, judgments, and estimates. The Statement of Changes in Equity and Statement of Cash Flows — both flagged as out of scope in the original pass — are now built; see below.

### How the Rental Services Module keeps deposits and revenue correctly separated

A new "Rental Services" section — Rental Items, Rental Agreements with a full check-out/check-in lifecycle, and a revenue/utilization report — built as a genuinely new business domain, not a variant of Sales.

- **A rentable item doesn't duplicate anything**: it's just a reference to something you already have — an existing Fixed Asset (equipment/vehicles, already depreciating on their own IAS 16 schedule, which renting out doesn't change) or an existing Product (identical units held as stock, e.g. a fleet of the same tool). `rental_items` links to one or the other; nothing about the underlying asset/product record changes.
- **Deliberately its own billing flow, not a reuse of Sales Invoices**: the existing `sales_invoice_lines` table requires a stock product on every line and posts revenue through one flat `sales_revenue` mapping shared by every invoice in the system — which would bury rental income inside ordinary goods-sales revenue rather than its own disclosed line, a real IAS 1 presentation concern for a business where rental is a distinct revenue stream. Rental charges (`rental_charges`) post directly to a dedicated **Rental Income** account instead. The trade-off, stated plainly: rental charges don't appear in the general Sales Invoice list — the same trade-off Income/Expense quick-entry already made for the same reason.
- **Security deposits are a liability, not revenue, until they stop being refundable**: collected into a dedicated **Rental Deposits Held** account (Dr Bank / Cr Deposits Held), refunded back out the same way (Dr Deposits Held / Cr Bank), and only recognised as Rental Income at the moment they're actually forfeited (Dr Deposits Held / Cr Rental Income) — never treated as earned revenue while the obligation to return the cash still exists.
- **Rental Asset Management** (added after the initial module): condition tracking at check-out and check-in (excellent/good/fair/damaged, with notes) so a damage dispute has something to point to — and checking an item in as "damaged" automatically routes it to `maintenance` status rather than back to `available`, since a damaged item isn't actually ready to rent out again just because the paperwork is done. Maintenance itself is a real workflow (scheduled → in_progress → completed), with a real operating expense posted to a dedicated **Repairs & Maintenance Expense** account the moment it's completed (Dr Repairs & Maintenance / Cr Cash-or-Bank) — a rental item that needs constant repair should show up as a cost problem in the P&L, not get quietly absorbed. The new asset utilization report (`/rental/reports/asset-utilization`) answers "is this item worth what we paid for it": rented days vs. period days, revenue earned, and maintenance cost incurred, per item. Verified live: checked an item in as damaged and confirmed it landed in `maintenance` (not `available`); ran the full schedule → start → complete cycle with a real GHS 75 cost and confirmed the exact Dr/Cr posting in the database; confirmed the utilization report's math directly (5 rented days out of a 10-day period = 50%, GHS 75 maintenance cost against GHS 0 revenue for that specific agreement = -75 net contribution).
- **Rental Workspace** (`/rental/workspace`): a landing page matching every other module's Workspace convention (Procurement, Sales, Accounting, etc.), built around a specific 10-KPI brief — Active Rentals, Available Assets, Reserved Assets, Assets Under Maintenance, Rental Revenue, Overdue Returns, Expiring Contracts, Outstanding Customer Payments, Asset Utilization Rate, and Monthly Profit Analysis — plus a "Needs your attention" feed and an "Upcoming Returns" rail. Two of these ("Reserved Assets" and "Outstanding Customer Payments") needed genuinely new backend work, not just repackaging existing data:
  - **Reserved Assets** = items with a `draft` agreement booked ahead but not yet checked out — distinct from `rented` (already checked out). A draft agreement doesn't change the item's status, so this is computed by cross-referencing draft agreements against their items.
  - **Outstanding Customer Payments** required building the other half of rental billing: `rental_charges` already posted Dr AR / Cr Rental Income the moment a charge was billed, but there was no way to record that a customer had actually paid it. New `rental_payments` table and `POST /rental/agreements/:id/payments` endpoint (Dr Bank / Cr Accounts Receivable) close that gap — outstanding is simply total billed minus total paid, company-wide, as a point-in-time balance (not scoped to the selected period, since an unpaid charge from months ago is still outstanding today).
  - **Monthly Profit Analysis** = Rental Revenue − Maintenance Cost − Depreciation, for the selected period. Depreciation only applies to the subset of rental items backed by a real Fixed Asset (traced via `rental_items.fixed_asset_id` into the existing `asset_depreciation_entries`) — product-backed items don't depreciate, so they contribute revenue and maintenance cost but no depreciation line.
  - **Asset Utilization Rate** here is a single company-wide aggregate (total rented-days across every item ÷ total possible item-days in the period) rather than the per-item breakdown the existing utilization report already provides — the two are complementary, not duplicates.
  - Verified end-to-end on a running server with a genuinely rich scenario (one active rental partially paid, one item mid-maintenance, one item reserved via a draft agreement, one item plainly available) and checked every one of the 10 numbers by hand: 4 active-vs-available-vs-maintenance-vs-reserved asset counts, revenue of exactly the billed amount, an outstanding balance of exactly billed-minus-paid, an expiring-contracts count that correctly landed on the 7-day boundary, and a utilization rate that matched the hand-calculated fraction (5 rented days ÷ 116 possible item-days = 4.310344...%) to full floating-point precision.
- **Double-booking is actually prevented**, not just discouraged: creating a new agreement checks for any other draft/active agreement on the same item with an overlapping date range and rejects the request outright.
- Verified end-to-end on a running server, every number checked directly in the database rather than just "the request succeeded": created an item and agreement, confirmed a genuinely overlapping second agreement gets rejected, checked out (item status → rented), collected a GHS 200 deposit, billed a GHS 300 rental charge at 15% VAT, checked in on time (0 overdue days), and refunded the deposit. Every journal entry checked line by line — the deposit collection and refund net to exactly zero in Rental Deposits Held, and the charge split correctly into Accounts Receivable (345), VAT Payable (45), and Rental Income (300), exactly 300 × 1.15. One real bug found and fixed while verifying: a wrong column name (`fa.asset_name` instead of the actual `fa.name`) in the rental items query.

- **Manufacturing Workspace** (`/manufacturing/workspace`, added after the initial module): a landing page matching every other module's Workspace convention (Procurement, Rental, Accounting, etc.) — Active/Draft Work Orders, Work in Progress value, Raw Materials on hand, Cost of Goods Manufactured, and Overhead Variance as KPIs; a "Needs your attention" feed for draft work orders (materials not yet issued) and a significant overhead variance (more than 10% of applied); and a "Recently Completed" rail. Built entirely from existing endpoints (`/manufacturing/work-orders`, `/manufacturing/manufacturing-account`, `/manufacturing/overhead-variance`) — no new backend code. The "significant variance" check guards against a zero-applied-overhead period (a company with no work orders yet, or one that hasn't assigned overhead rates) dividing by zero and showing NaN — verified directly against a real response where `applied` was 0.
  - **Drill-down** (added after the Workspace itself): every KPI card, feed item, and "Recently Completed" entry is a real navigation link, not just a static number. Since Manufacturing is one route with internal tabs rather than separate routes per section, drilling down means landing on the right tab — and for a specific work order, that record already selected — via React Router's `location.state` rather than a plain URL: `Manufacturing.jsx` reads `{ tab, workOrderId }` off navigation state on arrival and initialises accordingly. Work in Progress / Raw Materials / Cost of Goods Manufactured route to the Manufacturing Account tab; Overhead Variance and the variance warning route to COGM & Variance; every draft or completed Work Order routes straight to that specific record on the Work Orders tab, matching the same `.kpi-card-link` hover affordance the Executive Dashboard's own drill-down already established, reused here rather than reinvented.

- **Five costing methods** (added after the initial module): each Bill of Materials can be flagged with the costing method that fits it — Standard, Actual, Job, Process, or Activity-Based Costing. Two of these already existed without being labelled as such: **Job Costing** is exactly what the Work Order system already does (each Work Order is its own job accumulating its own costs) — formalised as an explicit `/manufacturing/job-cost-report`. **Actual Costing** is exactly the Manufacturing Account statement above (real FIFO/weighted-average material cost, real labour, real overhead incurred) — every Work Order already uses actual costs regardless of which method is layered on top. The other three are genuinely new:
  - **Standard Costing**: a `standard_cost_cards` row sets what a BOM's materials, labour, and overhead *should* cost per unit; `/manufacturing/work-orders/:id/standard-variance` compares a real completed Work Order's actual cost against that standard, scaled to quantity produced, computing Material/Labour/Overhead variances with the conventional favourable/unfavourable sign convention.
  - **Process Costing**: for continuous, homogeneous production tracked per period rather than per discrete job — a `process_cost_batches` row records units completed, units still in process with an estimated % completion, and period costs, from which equivalent units (completed + in-process × %) and cost-per-equivalent-unit are computed. The % completion is entered directly rather than guessed at — a real production judgement call this system has no sensor data to infer.
  - **Activity-Based Costing**: overhead allocated by multiple cost drivers (machine setups, inspections, material moves), each its own `abc_activity_pools` pool and rate — a genuine alternative to the Overhead Rates tab's single predetermined rate, not a replacement of it. A Work Order can use either method, or both.
  - **A real, financially significant bug found and fixed while building this**: `workOrderCostSummary` (which feeds both the Work Order detail page *and* the unit cost `completeWorkOrder` uses to receive finished goods into inventory) and `cogmStatement`'s overhead figure both only summed the single-rate `work_order_overhead_applications` table — silently ignoring any overhead applied via the new ABC allocation path. For any Work Order costed with ABC, this would have understated the finished good's true unit cost at completion *and* left Work in Progress permanently non-zero, since ABC-allocated overhead debited WIP but was never counted when clearing it. Caught by testing ABC allocation against a real Work Order and noticing the Job Cost Report's overhead column stayed at zero despite a real GHS 200 allocation just posted — fixed in both places, then re-verified.
  - Verified end-to-end on a running server: created a real BOM, Work Order, and standard cost card, and confirmed the variance report's material/labour/overhead figures matched an independent hand calculation exactly (GHS 1,000 / 50 / 600 favourable, GHS 1,650 total). Verified Process Costing's equivalent units (200 completed + 50 units at 40% = 220 equivalent units) and cost-per-unit (GHS 9,000 ÷ 220 = GHS 40.909...) to full floating-point precision. Verified ABC allocation's rate (GHS 5,000 ÷ 100 = GHS 50/setup) and resulting GL entry (4 setups × GHS 50 = GHS 200, posted Dr WIP / Cr Manufacturing Overhead Applied) directly in the database — then, after the bug fix above, re-confirmed the Job Cost Report and Work Order detail page both correctly reflect that GHS 200.

### How Manufacturing Settings, Bin Cards, Company Logo, Org Structure, and the sidebar accordion arrived

This batch came in as an uploaded zip rather than something built in this visible session — audited file-by-file against the committed state before merging anything (same discipline as every other uploaded batch this project has absorbed): read every diff, traced the real `movementType` values each posting controller actually uses to confirm the new Bin Cards feature's IN/OUT classification was accurate rather than assumed, and independently re-verified the headline claims live against a running server before trusting them.

- **Manufacturing Settings** (`/manufacturing/settings`, new `manufacturing_settings` table): one configurable row per company — a default warehouse for new Work Orders (falling back to the company's first warehouse if none is set, rather than blocking work order creation on a mandatory pick), a default overhead allocation base, a default costing method for new BOMs, and an overhead-variance significance threshold. That last one is a real improvement to existing code: the Manufacturing Workspace's "is this variance significant" check had been a hardcoded 10% in the frontend — now it's a genuine per-company setting, computed server-side and returned as `isSignificant`/`variancePct`/`thresholdPct` on `/manufacturing/overhead-variance` itself.
- **Bin Cards** (`/inventory-reports/bin-card`, new `bins` table): the traditional warehouse bin card — a running per-item, per-location balance with every receipt and issue. Auto-provisioned the first time a product is received into a warehouse (`stockService.receiveStock` now calls a new `getOrCreateBin` before doing anything else, inside the same transaction) rather than requiring manual setup before stock can arrive, with a one-time backfill for pairs that already had stock history. Verified live: the bin card's computed running balance for a real product/warehouse matched `stock_levels.current_quantity` exactly (40 units, independently).
- **Company Logo**: reuses the existing generic attachment system (the same one tasks/invoices/employees already use) rather than a parallel upload mechanism — a new `company` attachment type, viewable by anyone in the company but only uploadable/removable with `system.company.manage`. The `CompanyLogo` component fetches it as an authenticated blob and renders it via an object URL rather than a plain `<img src>`, since a plain image tag can't carry the Authorization header this system's file downloads require.
- **Organization Structure** (`/hr/organization-structure`): builds a management tree from the existing employee list — anyone whose manager isn't in the (filtered) list becomes a root, which naturally handles real roots, a manager who's been filtered out (e.g. terminated), and a stray/broken `manager_id` without special-casing any of them separately.
- **Sidebar accordion redesign**: changed from independently-collapsible sections (tracked per-section) to a single-open accordion — opening one module's section closes whichever was open, and the section containing wherever navigation actually landed (a sidebar click, browser back/forward, or a direct link) auto-opens, rather than leaving the active page's module collapsed and its own current page hidden.
- **Secondary theme color**: Theme Settings gains an independent sidebar-background color axis (nine dark presets — Warm Charcoal, Deep Navy, Espresso Brown, and others) alongside the existing accent color, deliberately kept to dark options only, since the sidebar's light text/icon colors are tuned for a dark background and a light secondary preset would silently break that contrast.

### How School Management works, and what it maps onto

The requested spec covers 16 sub-modules, but a genuine majority of it already exists in Bizness-OS and doesn't need rebuilding under a school-specific name:

- **Staff Management** → the existing HR & Payroll module. A school's teachers and support staff are just employees, tracked exactly the same way any other company's staff already are (attendance, payroll, leave, contract terms for part-time/visiting staff).
- **Accounting and Finance** (Payments, Receipts, General Ledger, Petty Cash, Trial Balance, Financial Statements including Cash Flow) → the existing Accounting & Finance module, in full — Petty Cash already exists (`petty_cash_accounts`/`petty_cash_vouchers`), as does the full Trial Balance/Balance Sheet/Income Statement/Cash Flow Statement suite.
- **Inventory Management** (school assets, stationery) → the existing Inventory & Warehouse module.
- **Communication** (SMS, email, announcements) → the existing Communications module.
- **Reports** → the existing Reports infrastructure, extended with school-specific reports as later phases add the data to report on.

**What's genuinely new** — Phase 1, built here, is the foundation everything else (Attendance, Examinations, Fees, Timetable, Library, Transport, LMS) will hang off in later phases:

- **Classes**: a grade/section for a given academic year, with its own class teacher and capacity.
- **Guardians**: kept as their own record rather than fields on a student, since one guardian is very often linked to more than one student (siblings) and a student can have more than one guardian — a real many-to-many relationship with a primary-contact flag.
- **Students**: the core enrollment record, with a real status (applicant → enrolled → withdrawn/graduated) rather than deleting and recreating records across that transition.
- **Admissions**: a real pipeline (submitted → under review → documents pending → approved/rejected → enrolled) — students are never created directly from an application; an "Enroll" action is the one deliberate transition point from applicant into an actual student record, and it's blocked unless the application has genuinely been approved first.

Verified end-to-end on a running server: created a real class, a real guardian, and a real student linked to both, and confirmed the class's enrolled-student count updated correctly; ran a full admissions application through its real lifecycle — submitted, approved, then enrolled — and confirmed a genuine new student record was created with its own generated student number, the application correctly marked enrolled with a trace back to the new student, and the workspace dashboard's counts reflected all of it accurately. Deliberately tried to re-enroll an already-enrolled application and delete a class with real students still assigned — both correctly rejected.

Later phases will add: Admissions document handling, Examinations & Assessment (marks entry, report cards, grading, the Reading/Writing/Fluency skill tracking specifically called out in the spec), Fees Management (tuition invoicing, most likely built on top of the existing Sales & Distribution AR pipeline the same way Service Business's invoicing was), Timetable Management, Library Management, Transport Management, and Learning Management (assignments, study materials).

**Phase 2 — Student Attendance** (built after Phase 1): distinct from staff attendance (the existing HR shift/clock-in tracking) — this is per-student, per-class daily attendance, matching the real teacher workflow of "see the whole roster, mark the exceptions" rather than entering every student one at a time regardless of outcome.

- A real `UNIQUE(student_id, attendance_date)` constraint means marking a student twice for the same day always **corrects** the existing record via an upsert rather than creating a duplicate — the same "one authoritative row per period" discipline already used elsewhere in this system (e.g. one active employee contract term at a time).

### Recoloring the sidebar logo to match whatever secondary color is chosen — keeping the metallic gold fixed, and being honest about where the technique itself breaks down

A request with a real, specific constraint: the logo's gold should never change, but everything else in it should automatically harmonize with whichever sidebar color a company has picked, rather than staying a fixed blue regardless of what's around it.

**Checked the logo's actual pixel data before assuming any technique would work on it.** Sampled the hue of every non-transparent pixel across the real file and found something genuinely useful: the entire logo sits in exactly two clean, non-overlapping hue bands — gold roughly 34–51°, blue roughly 208–235° — with nothing at all in between. That gap is what makes a reliable, automatic separation possible at all: shift the hue of every pixel that falls in the blue band to match a target color, while leaving every gold pixel completely untouched, and the original gradients, bevels, and highlights all survive intact since only the hue changes, never the saturation or brightness that give the logo its metallic look.

**The one thing this technique cannot paper over, and didn't try to: three of the nine sidebar color presets sit too close to the logo's own gold to recolor into safely.** Charcoal, Espresso, and Stone are all warm, low-saturation near-blacks in roughly the same 23–38° hue family as the logo's gold itself — recoloring the blue wordmark to match any of them would shift it into that same warm family, and the gold accents that are supposed to stand out against it would stop being visually distinct from the wordmark around them. Found this by actually generating the recolored result and looking at it, not by reasoning about hue distance in the abstract — the rendered comparison showed the wordmark and its gold accents blurring into a single, muddier color, exactly what the numbers predicted but confirmed rather than assumed. The fix for those three specific presets is to not recolor at all: the original blue logo already reads cleanly against a warm, dark-neutral background on its own, confirmed the same way, by rendering it there and looking.

Generated all eighteen resulting variants (nine secondary presets × two logo assets, the full wordmark and the compact rail mark) once, as static files, rather than attempting this as a live, in-browser transform — the nine sidebar colors are a small, fixed, known set, not something visitors define freely, so pre-rendering is simpler and faster than reprocessing pixels in the browser on every theme change. `getSidebarLogoSrc()` picks the right file for the currently active secondary color; the six genuinely recolored presets get their own file, the three excluded ones fall back to the original, and an unrecognized key falls back the same way rather than constructing a path to a file that was never generated.

**A real bandwidth cost worth being upfront about, and worth fixing rather than shipping as-is**: eighteen new full-resolution PNGs added roughly 5.4MB to what a first-time visitor downloads, a real number given this project has repeatedly discussed the actual connectivity constraints of its own target market. Compressed every generated file through `pngquant` afterward and checked the result visually rather than assuming a quality setting was safe by the number alone — at this file's resolution and color complexity, an 80–95% quality target brought the total down to roughly 1MB with no visible difference in the metallic gradient or bevel detail across multiple hue families checked side by side. The PWA's own precache size reflects this directly: 8.1MB with the uncompressed files, 3.7MB after — barely more than the 2.7MB this project shipped with before any of this feature existed.

Updated the existing Sidebar test suite, which broke immediately and predictably the moment the component started calling `useTheme()` for the first time — added the missing mock rather than working around it. ### Giving the migration runner real tracking — and handling what that means for a database it already fully migrated the old way

Replaced the migration runner with a version that tracks what it's actually applied in a `schema_migrations` table, so running it again only picks up genuinely new files instead of re-executing every migration from scratch. This directly fixes a limitation named explicitly elsewhere in this document, from back when the backup/restore feature was built: a restored backup could be applied cleanly over an already-migrated database specifically because `pg_dump --clean --if-exists` handles the drop-and-recreate itself, working around "the failures this app's own migration runner is prone to" — the old runner had no memory of what it had already done, so simply running it twice against the same database would fail the moment it hit a `CREATE TABLE` for something already there.

**The real risk in swapping this in wasn't the new script itself — it was every database this project has already been building against for months.** A tracking table that starts empty can't tell "this is a brand new database" apart from "this database was fully migrated already, just never by anything that wrote any of it down" — and treating the second case like the first would mean the very next migration run tries to recreate every table this whole project already depends on, failing immediately and for a confusing reason if you didn't already know why. Checked for this directly rather than assuming a fresh install was the only scenario that mattered: this project's own main database, accumulated since the very first migration, had exactly this shape — real data, real structure, and no tracking table at all, since nothing before this added one.

Handled by checking, before ever touching anything, whether a table from the very first migration already exists. If it does and the tracking table doesn't, every `.sql` file currently on disk gets recorded as already applied — a one-time backfill — before the normal apply loop ever runs, so an existing database picks up real tracking going forward without a single migration being touched or re-attempted.

Verified all four shapes this needed to handle correctly, not just the happy path: a genuinely fresh database (all 74 apply cleanly, correctly reported); the same database run a second time (all 74 correctly skip, zero re-execution); a database simulating exactly this project's own real history — migrated once, tracking table then removed to reproduce "never tracked to begin with" — correctly detected and backfilled rather than failing; and, with a real new migration file added afterward, only that one file actually applying while the other 74 stay skipped. Ran the real, final script against this project's own accumulated main database directly and confirmed the backfill fired for real (74 backfilled, 0 re-applied), then confirmed every table and every row — the demo company, its users, its full audit history — came through completely untouched. 206 backend tests, unaffected, since this script isn't part of that suite but the rest of the backend obviously needs to still work against a database it just backfilled.

### Deploying the frontend to GitHub Pages — and fixing the real bug from the earlier hosting discussion that this would have hit immediately

Built the actual deployment path discussed earlier in this project: GitHub Pages for the frontend (genuinely satisfies the HTTPS requirement installability needs, for free), with the backend deployed separately since Pages cannot run a long-lived process at all. This is not a hypothetical setup — the fix below was necessary specifically because this configuration was actually being built and tested, not assumed to work.

**The real bug, found and fixed rather than worked around**: the login-refresh cookie was hardcoded to `SameSite=Strict`. That's the safer setting when frontend and backend share a domain, but it silently drops the cookie on every cross-site request — including the frontend's own legitimate calls — the moment they're on genuinely different domains, which GitHub Pages plus a separately-hosted API always is. Left as-is, this would have meant the silent-login-refresh flow this app relies on failing outright for every visitor: sign in, close the tab, come back, already signed out, every time — not an edge case, the normal case.

**Fixed by making the cross-site behavior explicit and opt-in** (`COOKIE_CROSS_SITE`), rather than either leaving the default broken for this deployment shape or silently downgrading every deployment's security by defaulting to the more permissive setting. Same-domain deployments (Render, a custom domain, local dev) keep `Strict` — the genuinely safer choice — completely unchanged. Only a deployment that explicitly declares itself cross-site gets `SameSite=None`, and that setting is only ever valid together with `Secure=true` (browsers reject the cookie outright otherwise) — the two are forced on together in code, not left as two separate settings someone could configure inconsistently.

**A second, independent bug found while fixing the first, worth naming since it predates this change entirely**: the cookie-clearing call on logout never specified `sameSite`/`secure` at all, while the cookie-setting call did. A mismatch between the attributes a cookie is set with and the attributes used to clear it can mean the browser doesn't recognize them as the same cookie and silently leaves the original in place — meaning logout may not have been fully clearing this cookie even before any of today's changes, in ordinary same-domain use. Fixed by having both calls reference the exact same logic, so they can never drift apart again.

Verified the critical constraint directly: reverted `Secure` to ignore the cross-site setting in the real source and confirmed the specific test built for that exact pairing failed, not a generic one. Restored the fix, confirmed all 7 new tests and the full 206-test backend suite pass.

**The GitHub Pages deployment itself**: a workflow that builds and publishes `client/` on every push to `main`, with two things that needed real verification, not just written and assumed correct. A GitHub Pages project site serves from `/repo-name/`, not the domain root — the app's asset paths, the PWA manifest's `start_url`/`scope`/icon paths, and React Router's own routing all silently break under a subpath unless every one of them is told about it consistently. Made this configurable via `VITE_BASE_PATH`, defaulting to `/` so every existing deployment (Render, local dev) is completely unaffected, and confirmed this two ways: built locally with a simulated subpath and inspected the actual output — every asset reference, every manifest field, correctly prefixed — then rebuilt with no override at all and confirmed the output was byte-for-byte the same shape as before this change existed. GitHub Pages also has no native concept of client-side routing — visiting a deep link directly 404s before React Router ever runs — so the workflow copies the built `index.html` to `404.html`, the standard way of making Pages serve the SPA shell for any unmatched path instead of a real error.

**What this doesn't do, worth being direct about**: it deploys the frontend only. The backend — Postgres, the Express API, the background schedulers — still needs deploying separately (Render, per the earlier recommendation), with its URL supplied to this workflow as a repository variable (`VITE_API_URL`) and `COOKIE_CROSS_SITE=true` set on that backend deployment specifically. Neither of those is something that can be done from inside this codebase — they're real accounts and real deployments the project's owner has to create.

### Making the app usable offline — reading yes, writing no, and being honest about exactly where that line sits

A deliberate scope decision came before any code: this app now supports genuine offline *reading*, and a clean, honest block on offline *writing* — not queued-and-replayed offline writes, which is a real, meaningful risk in a double-entry accounting system, not a corner case worth hand-waving past. Queuing a journal entry, a stock adjustment, or an invoice while offline and silently replaying it later means validating it against data that was already stale the moment it was queued — the server-side checks this app already relies on (balance checks, row locking, current stock levels) only mean something against *current* state. Two people queuing conflicting stock adjustments offline, synced in sequence, can silently produce a number neither of them actually intended. Telling someone plainly "reconnect to save this" is a better outcome than letting them believe an action already succeeded when it might not have.

**Reading**: a `NetworkFirst` runtime-caching rule, scoped specifically to `GET` requests under `/api/` — the network is always tried first and always wins when it's available; the cache is only ever consulted when the network genuinely fails, and even then only for up to an hour, since a week-old cached balance is worse than no offline view at all. This is a deliberately different choice from `stale-while-revalidate` or `cache-first`, either of which would risk quietly showing stale financial data even while online. Verified this is genuinely GET-only by inspecting the compiled service worker directly, not just trusting the config — the method check compiles into the actual route matcher.

**Writing**: blocked at the application layer, in `api.js`'s request interceptor, before a mutating request (`POST`/`PUT`/`PATCH`/`DELETE`) is even attempted while offline — with a clearly identifiable error (`isOfflineWriteBlock`) the UI can catch and explain plainly, rather than a generic network failure. `navigator.onLine` can occasionally under-report true connectivity, so this is a fast first check, not the only line of defense — a request that slips through with a stale "online" reading still fails naturally through the ordinary error path.

### Moving tokens out of localStorage

A security review found both the access token and the 7-day refresh token were being kept in `localStorage`, readable by any JavaScript running on the page — meaning a single future XSS bug (none currently exist in this codebase, but the whole point of defense in depth is not needing that to stay true forever) could hand an attacker a long-lived credential outright.

**The refresh token now lives in an `httpOnly` cookie**, set by the server on login (`Set-Cookie: refreshToken=...; HttpOnly; SameSite=Strict; Path=/api/auth`). This is the real fix — an `httpOnly` cookie is structurally invisible to `document.cookie` and every other DOM API, so no injected script can ever read it, not even in principle. Scoped to `Path=/api/auth` specifically, so it isn't sent on every ordinary API call, only the two endpoints that actually need it. `login` sets it, `refresh` reads it instead of expecting it in the request body, and `logout` both revokes the underlying session in the database and clears the cookie.

**The access token moved to an in-memory JS variable** (a new `tokenStore.js`, deliberately a plain module-level variable rather than React state, since axios interceptors run outside any component and need synchronous access on every request). It no longer persists across a reload — instead, `AuthContext`'s initial load now attempts a silent `/auth/refresh` using the `httpOnly` cookie first; if a valid session exists, the person is transparently signed back in without re-entering a password, and if not, they land on the login page, the same end result the old localStorage check used to produce either way.

Verified the actual mechanics with raw `curl`, not just trusting the code: confirmed the `Set-Cookie` header genuinely carries `HttpOnly`, `SameSite=Strict`, the scoped path, and the correct 7-day expiry; confirmed the login response body no longer contains a `refreshToken` field at all; confirmed `/auth/refresh` succeeds using only the cookie with no request body; confirmed it's correctly rejected with no cookie present at all; confirmed `logout` both clears the cookie on the response and genuinely revokes the session in the database — tested by then replaying the *same* now-revoked cookie against `/auth/refresh` and confirming it's rejected, not just theoretically expected to be.

### Rate limiting beyond just /login

A security review found rate limiting existed on exactly one endpoint — `/auth/login` — leaving roughly 400 other endpoints across the entire app, including password reset, account registration, and MFA verification, with no protection at all.

Added two layers rather than one blanket rule, since a single number can't be right for every kind of endpoint:

- **A general limiter on everything under `/api`** (1000 requests / 15 minutes per IP) — applied once at the top of `server.js` rather than touching 70+ individual route files. Deliberately generous rather than tight: this is a B2B app where an entire office can sit behind one shared public IP through NAT, and a strict global limit would risk locking out multiple legitimate simultaneous users, not just an attacker.
- **A much tighter limiter on genuinely sensitive, low-frequency actions** (10 / 15 minutes): company registration, password reset requests, and password reset submissions. Nobody legitimately does any of these dozens of times in 15 minutes, so a strict cap here doesn't risk real usage the way the same number would on ordinary endpoints.
- **A dedicated limiter on MFA code submission**, same 10/15-minute cap — a TOTP code is only 6 digits (1 in 1,000,000), and without a limit here an attacker could feasibly brute-force one within traffic that looks otherwise unremarkable.

Verified live against a running server, not just configured and assumed: confirmed a normal login and an authenticated request both still succeed with the new limiters in place, and that the response correctly carries live `RateLimit-*` headers. Then specifically drove the sensitive-action limiter to its actual threshold — 12 requests to `/forgot-password` in a row — and confirmed the 10th succeeds while the 11th and 12th are genuinely rejected with 429, proving the limiter fires at the configured number rather than just trusting the configuration value was correct.

### Rotating the JWT secrets off their placeholder defaults

### Adding a Statement of Financial Position for School

### How the Compliance Calendar works

The Executive Dashboard's existing Compliance widget (037) only ever tracked point-in-time status — is SSNIT/PAYE/VAT currently valid, expiring, or expired? ### How Employee Contract Terms work

Excluding Part Time, Contract, Trainee, and Internship staff from the standard payroll run (above) only answers half the question — they still need to get paid, just not necessarily through the same fixed SSNIT+PAYE rule every full-time employee uses. Each such employee can now have a **Contract Term**: their salary, and individually which of Ghana's three pension tiers apply, whether PAYE applies, or whether Withholding Tax applies instead — since a genuine independent contractor relationship has no SSNIT at all (no employer-employee relationship for it to attach to) and is normally taxed via a flat withholding rate instead.

- **Ghana's real 3-tier pension structure**, reflected in the default rates: **Tier 1** (13.5% combined — 5.5% employee + 8% employer) is the mandatory scheme SSNIT itself collects. **Tier 2** (5%, employer-only) is also mandatory, but paid to a licensed *private* trustee, not SSNIT — a genuinely different destination, which is why it posts to its own **Tier 2 Pension Payable** account rather than folding into the existing SSNIT Payable. **Tier 3** is entirely voluntary, no fixed rate.
- A contract term is either an employment relationship (PAYE) or a contractor relationship (Withholding Tax) — never both; enforced by both a database CHECK constraint and the API, not just the frontend form.
- Only one contract term is active per employee — creating a new one automatically deactivates whichever was active before, so payroll always has one unambiguous answer for "how is this person taxed right now."
- A non-full-time employee with **no** contract term is correctly skipped by payroll entirely (not run through any default assumption) — the point of this feature is that guessing is worse than asking, so the system simply doesn't guess.
- Full-time employees are completely unaffected: `processPayrollRunCore` and `buildPayrollJournalLines` were extended, not replaced — every new field is additive and defaults away to the exact original behaviour when absent, verified by re-running the existing `payrollService.test.js` suite unchanged (all 14 tests still pass) after the change.

Verified end-to-end on a running server with a genuinely stress-testing mix: a contractor with Withholding Tax only (15%, no SSNIT at all), a part-timer with Tier 1 only, a trainee with **nothing** enabled (a pure stipend), an intern with **every** component switched on at once (Tier 1 + Tier 2 + Tier 3 + PAYE, to stress-test the full combination), and the existing full-time employee alongside them, unaffected. Every single payslip figure — for all five people — matched an independent hand calculation exactly. The resulting journal entry balanced precisely (GHS 12,361 debits = GHS 12,361 credits) across eight lines spanning Salaries & Wages, the pension expense, SSNIT Payable, Tier 2 Pension Payable, Tier 3 Provident Fund Payable, Withholding Tax Payable, and Net Salaries Payable — checked line by line against hand-computed expectations, not just confirmed as "balanced." Also verified both safety rails work: attempting to set contract terms on a full-time employee is rejected, and attempting to enable both PAYE and Withholding Tax on the same term is rejected.

### How payroll decides which employees to include

Only **full-time** employees go through the standard SSNIT/PAYE payroll run — contract, part-time, internship, and trainee staff are excluded, even if their status is active. This was a real behavioural change, not always the case: the employee-selection query used to only check `employment_status` (active/on_leave), so a contract worker or intern with a salary on file would have been run through exactly the same SSNIT and PAYE math as a full-time employee, which doesn't reflect how these are actually compensated and taxed in Ghana (contractors are typically subject to a flat withholding tax with no SSNIT at all, since there's no employer-employee relationship; interns and trainees are frequently on a stipend outside the standard payroll cycle entirely).

### How Automatic Payroll Run works

Today, running payroll was entirely manual every month — someone had to remember to open HR & Payroll, create a run, and process it. ### How the Manufacturing Accounting Module implements IAS 2 (Inventories)

A new "Manufacturing" section — Bill of Materials, Overhead Rates, Work Orders, and a Cost of Goods Manufactured / overhead variance report — built as a genuinely new, real costing engine, not a mock. This is a large module in its own right; here's the scope and the design decisions that keep it low-risk against everything else in the system.

- **IAS 2.10** requires manufactured inventory's cost to include direct materials, direct labour, and a systematic allocation of production overhead (together, "conversion costs"). A Work Order accumulates all three in Work in Progress as they happen — issuing materials, logging labour hours, and applying overhead — then moves the total into finished-goods stock at a computed full-absorption unit cost when completed.
- **IAS 2.13 — the rule most systems get wrong** — is why `manufacturing_overhead_rates` stores a `normal_capacity` figure (budgeted labour hours or units for a typical period) rather than actual output: overhead is applied to a Work Order at a *predetermined* rate × actual activity, never actual overhead incurred ÷ actual output, which would let idle-capacity cost quietly leak into inventory value. The difference between overhead applied this way and actual overhead incurred is a real, trackable variance (`/manufacturing/overhead-variance`), closed out to expense each period rather than silently absorbed.
- **Deliberately low-risk against every existing module**: only one new balance-sheet account was introduced (Work in Progress). Raw materials are still received through the existing GRN/Purchase Invoice flow into the existing Inventory account — nothing there changed. A completed Work Order's finished goods flow back into that *same* existing account rather than a separate Finished Goods control account, which means a manufactured product is immediately, fully sellable through the existing Sales Order → Delivery → COGS pipeline with zero code changes there. Verified directly, not assumed: created a real Work Order, ran materials issue → labour → overhead → completion, then sold two of the five units produced through the ordinary, completely unmodified Sales Order → Delivery flow — COGS posted at exactly GHS 1,840 (2 units × the GHS 920 computed unit cost), and the ledger stayed balanced throughout.
- **Every number in the test run was hand-verified against the database**, not just "the request succeeded": 10 units of raw material issued at GHS 400 (GHS 4,000), 10 labour hours at GHS 50 (GHS 500), overhead applied at the predetermined rate (GHS 1,000 budgeted ÷ 100 normal hours = GHS 10/hour × 10 hours = GHS 100), completed at GHS 920/unit (4,600 ÷ 5) — every GL journal entry checked line by line, and Work in Progress nets to exactly zero once a Work Order completes.
- **Actual manufacturing overhead, by real category** (added after the initial module): the original design created one "Manufacturing Overhead — Actual" account meant to hold real factory overhead for the IAS 2.13 variance comparison — but no endpoint was ever built to post to it, so it had always shown zero. Replaced with ten dedicated, individually-postable accounts (Indirect Labour, Factory Rent, Utilities, Insurance, Security, Cleaning, Factory Depreciation, Factory Maintenance, Factory Management Salaries, and Internet) and a real recording endpoint (`POST /manufacturing/overhead-actual`, Dr [category] / Cr Bank) plus a matching form on the Reports tab — so a manufacturer can see exactly where overhead cost is going, not just one lump total. The first pass at this only built nine of the ten requested categories — "Internet" was missed — caught on review against the original request and added as its own follow-up migration (`046`) rather than silently reworking the first one, updating both the category whitelist and the variance calculation's account list to include it. "Factory Maintenance" is deliberately its own account, distinct from the Rental module's "Repairs & Maintenance Expense" added earlier — different cost pools that happen to share a similar name. "Factory Depreciation" is likewise separate from the general Depreciation Expense every fixed asset already posts to via Asset Management — this doesn't reroute that existing flow, a company records factory-attributable depreciation here manually if they want it counted as overhead. Verified end-to-end on a running server, including the fix specifically: recorded a real GHS 120 Internet charge and a GHS 300 Indirect Labour charge, confirmed the Internet charge posted to its own distinct account (checked directly in the database), and confirmed the variance report's category breakdown now lists all ten categories with Internet correctly showing GHS 120 and the total actual overhead correctly summing to GHS 420. Ledger stayed balanced throughout.
- **One real bug found and fixed while building this**: the existing product create/update endpoints didn't know about the new `product_type` field (trading / raw material / finished good) at all — fixed and verified before the rest of the module could be tested.
- **The Manufacturing Account statement** (`/manufacturing/manufacturing-account`, added after the initial module): the classic cost-accounting build-up — Opening Raw Materials + Purchases + Carriage Inward − Closing Raw Materials = Raw Materials Consumed, + Direct Labour + Direct Expenses = Prime Cost, + Factory Overheads = Factory Cost, + Opening WIP − Closing WIP = Cost of Goods Manufactured. Two new accounts (Carriage Inward, Direct Expenses) were added since nothing tracked either before — both ordinary expense accounts postable via the existing Expenses quick-entry. This is a genuinely different, complementary view from the Work-Order-based `cogmStatement` above: it uses **actual** factory overhead incurred (the real category accounts), the figure a formal cost statement would use, rather than overhead **applied** at the predetermined rate to individual work orders — the two will only agree in a period with zero overhead variance, and that's by design, not an inconsistency. Since raw materials share the same Inventory GL account as trading goods (no separate Raw Materials control account exists, by original design), Opening/Closing Raw Materials are reconstructed from stock movements filtered to `product_type = 'raw_material'` products — the same "closing is always real/today, opening is derived by working backward through the period's movements" approach the Statement of Cash Flows already uses for its own cash reconciliation. Verified end-to-end with a full, realistic scenario: 100 units of a raw material received (GHS 2,000), a further 50 units purchased mid-period via GRN (GHS 1,100), 60 units issued to a Work Order (GHS 1,240.002 at weighted-average cost), GHS 80 Carriage Inward, GHS 150 Direct Expenses, GHS 200 Direct Labour, and GHS 630 Factory Overheads (Rent + Utilities) — every single line of the statement matched an independent hand calculation exactly, down to the final Cost of Goods Manufactured of precisely GHS 860.00. One real test-setup bug caught along the way (not a bug in the statement itself): a product left flagged `product_type = 'raw_material'` from an earlier verification session was silently inflating the raw materials totals until spotted and reset.
- **Products.jsx** gained a Product Type selector so a company can flag which products are raw materials or finished goods — required before either can appear in a Bill of Materials.

### How the Statement of Cash Flows and Statement of Changes in Equity complete the primary IFRS set

Both new tabs on Financial Statements, in `ifrsAdditionalStatementsController.js` — the last two of the four primary IFRS statements, alongside the Statement of Financial Position and Statement of Profit or Loss above.

- **Statement of Cash Flows (IAS 7)** uses the indirect method (IAS 7.18(b)) — the near-universal choice in practice, since it starts from net income already computed for the P&L rather than requiring a parallel direct tally of every gross cash receipt and payment: Net Income → add back Depreciation (from `asset_depreciation_entries`, not an account-name guess) → adjust for working capital movement (every current asset/liability **except** cash/bank/petty cash themselves, computed generically from `account_subtype` rather than hardcoded account names, so a company's custom current-asset/liability accounts are picked up automatically) → Net Cash from Operating Activities. Investing activities come from `fixed_assets.original_cost` (capex, by `acquisition_date`) and `asset_disposals.proceeds`. Financing activities come from movements in `long_term_liability`-subtype accounts and equity accounts (excluding the profit-closing entries and revaluation entries below, which aren't real cash movements).
  - **Self-checking, not just computed**: the statement independently calculates the *actual* change in bank + petty cash balances over the period and compares it to the indirect-method result — a real reconciliation, the same "does this actually tie out" discipline as the Balance Sheet's `isBalanced` check. A live end-to-end test confirmed both numbers landed on exactly 1,520 with zero reconciling difference, not a coincidence-of-rounding but the classification logic genuinely being complete for that period's transactions.
- **Statement of Changes in Equity** rolls forward every equity account (Owner's Equity, Retained Earnings, Revaluation Surplus) from opening to closing balance, splitting movements into "Profit for the Year Transferred" (identified by the existing year-end close feature's `reference_type = 'closing'` — see `closingController.js`), "Revaluation Surplus Movement" (`reference_type = 'asset_revaluation'`, per the IAS 16.41 revaluation model already built into Asset Management), and "Other Movements" (everything else — capital contributions, drawings).
  - **Guaranteed to agree with the Balance Sheet, not just usually**: for any financial year not yet formally closed, Retained Earnings' closing balance folds in the same *unappropriated* current-year-profit calculation the Balance Sheet already uses for its "Current Year Earnings" line — so this statement's Total Equity can never show a different number than the Balance Sheet's Total Equity for the same date. Verified directly: with a real, non-zero net income in the test data, both endpoints independently returned 10,090 for the same date.

### How the Settings module works

**Consolidation**: Company Profile, Branches, Users, Roles & Permissions, Financial Years, Currencies & Exchange Rates, and Audit Trail were previously split across an "Administration" section and "Accounting & Finance" — they're now gathered under a single **Settings** section in the sidebar. No routes or permissions changed, only where each item is grouped (same pattern as the earlier Reports consolidation).

**Document numbering** (Settings → Company Profile): every document number in the system — invoices, POs, quotations, GRNs, receipts, credit/debit notes, RFQs, requisitions, contracts, leads, petty cash vouchers — used to be `${prefix}-${Date.now()}`. That's unique, but not what any business expects on a printed invoice, and it gives no sense of sequence or volume.

- **`document_number_sequences`** holds one counter per `(company, prefix, year)`. It's keyed by year so numbering resets every January regardless of whether the company's chosen format actually includes `{YEAR}` — that's what most businesses expect ("invoice #1" again each year, not a number that climbs forever).
- **Atomic by construction**: issuing a number is a single `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` statement, not a read-then-write — two requests racing for the same prefix in the same instant can never be handed the same number.
- **Format is per-company and configurable**: `companies.doc_number_format` (default `{PREFIX}-{YEAR}-{SEQ}`) and `doc_number_padding` (default 5) control the output — e.g. `INV-2026-00001`. The API rejects a format missing `{SEQ}` (documents from the same prefix/year would collide) and a padding outside 1–10.
- **`salesService.generateDocNo(client, companyId, prefix)`** is the single function every document-creating controller calls — it went from a synchronous one-liner to an async DB call, so all 22 call sites across 16 controllers were updated to `await` it with their transaction's `client`. Non-transactional creates (leads, contracts) pass the shared `db` pool instead, since issuing one number doesn't need multi-statement atomicity.
- **`GET /company/document-numbering`** returns the current format/padding plus every active counter, so Settings can show "next number" per document type without exposing the raw sequence table.

**Backup & Restore** (Settings → Backup & Restore, `system.backup.manage`): a real feature backed by the actual `pg_dump`/`psql` binaries already required to run this app — not a mock, not an application-level JSON export.

- **Download**: streams a live `pg_dump --clean --if-exists --no-owner --no-privileges` straight to the browser, never written to disk on the server. `--clean --if-exists` means the dump includes `DROP ... IF EXISTS` before every `CREATE`, so the file can be restored into a database that already has these tables without hitting the "relation already exists" failures this app's own migration runner is prone to.
- **Restore is deliberately hard to trigger by accident**: the uploaded file's buffer is piped directly into `psql`'s stdin (again, never touches disk) with `--single-transaction --set ON_ERROR_STOP=1`, so a failure partway through rolls the *entire* restore back rather than leaving the database half-restored. The request must also include the literal string `RESTORE` in a `confirm` field — enforced server-side, not just as a frontend checkbox someone could bypass by calling the API directly — and the frontend additionally requires typing that same word plus a second confirmation dialog before submitting.
- **Not company-scoped, deliberately**: a restore always covers the whole database (every company sharing these tables), the same way `npm run migrate` does — there's no safe way to "restore just one company's data" without risking foreign-key breakage against every other company. `backup_logs` records every attempt (success or failure, file size, who ran it) as an audit trail — it never stores the backup content itself.
- **Not auto-granted**: unlike most permissions this session added, `system.backup.manage` is deliberately *not* auto-granted to existing system roles when its migration runs — a destructive, whole-database operation should be an explicit opt-in via Roles & Permissions, not something that silently appears for every admin the moment the migration applies. Verified end-to-end: downloaded a real ~450KB backup covering all 134 tables, restored it back into the same database, and confirmed every figure (account count, ledger balance, table count, user records) matched exactly before and after — a true lossless round-trip, not just "the request returned 200."

**Theme** (Settings → Theme): light/dark mode plus a choice of 5 accent color pairs, both purely personal — stored in `localStorage`, not the database, the same way most software treats appearance preference (per-person, not company-wide). No backend or migration involved.

- Every color a component actually paints with is a CSS custom property, not a literal value — this required converting roughly 50 remaining hardcoded hex colors across `styles.css` into variables first (surfaces, hover states, badge/banner tints and borders, the scrollbar, skeleton loaders), since dark mode is only possible if *every* visual surface can be redefined. Four decorative KPI-card accent-stripe colors were deliberately left as fixed literals — they're meant to add visual variety regardless of which theme is active, not represent brand identity.
- Dark mode is its own warm, ledger-grounded palette (`[data-theme="dark"]` on `<html>`) — not a generic gray/black inversion. Primary green and gold both brighten slightly for contrast against a dark background; semantic status colors (success/warning/error/info) move from opaque pastel tints to translucent ones, since an opaque light-pink error banner would look like a mistake on a dark background. The sidebar needed no changes at all — it was already a dark warm charcoal in light mode by the original design.
- Accent presets (Cedi Green/default, Ocean Blue, Royal Indigo, Terracotta, Charcoal Slate) are matched primary+accent *pairs*, not a free color picker — keeps the "one signature accent, used with restraint" design principle intact no matter what someone picks.
- Applied twice: once synchronously in `main.jsx` before React's first render (reading directly from `localStorage`, avoiding a flash of the default theme on load), and again reactively via `ThemeContext` whenever the person changes it in Settings — including live-following the OS's light/dark setting when "Match device" is selected, via a `matchMedia` listener.

### How Procurement and Sales budgets always reconcile with Accounting & Finance's Budget

Rather than build a second, parallel budget system for Procurement and Sales, both get scoped read/write access to the *exact same* `budgets`/`budget_lines` tables Accounting & Finance's own Budgets page already manages — Procurement can see and edit Cost of Sales lines, Sales can see and edit Revenue lines, nothing else. Since it's literally the same rows, not a duplicate calculation running in parallel, these module budgets can never fail to add up to the company-wide budget — there's only one number for any given account/period, however many pages let you look at it or edit it.

- **New permissions, no new tables**: `procurement.budget.manage` and `sales.budget.manage`, each restricted server-side to their scope — enforced by checking the *real* `chart_of_accounts.account_subtype`/`account_type` of whatever line someone's trying to touch, not trusted from the request. A Procurement-only user hitting `PATCH /budgets/:id/lines/:lineId` on a Revenue line gets a 403, even if they somehow obtained that line's ID directly.
- **Shared `ModuleBudget.jsx` component** powers both new pages (`ProcurementBudget.jsx`/`SalesBudget.jsx`) — same UI, different `accountFilter` predicate — rather than two independently-maintained copies that could drift apart from each other.
- Creating an entirely new company budget stays `accounting.budgets.manage`-only (a bigger action than editing scoped lines); Procurement/Sales can add or edit lines within an existing budget, not spin up a new one.
- **Verified as a genuine access-control feature, not just a UI restriction**: created a real test role holding *only* `procurement.budget.manage`, logged in as it, and confirmed directly against the API — reading the budget succeeds, editing a Revenue line is blocked with a 403, editing a Cost of Sales line succeeds. Then logged back in as a full-access user and confirmed the *exact same* budget shows both that edit and an earlier admin edit to the Revenue line side by side — proving there's genuinely one shared number, not two independently-arrived-at figures that happen to match.

### How the Executive Dashboard follows its spec

Rebuilt against a specific 11-KPI / 8-chart / 7-insight / 10-item-compliance brief, with each piece either backed by real data or explicitly flagged where the underlying concept doesn't exist yet in this system — nothing on the dashboard is a placeholder number.

- **KPI cards**: all 11 (Total Revenue, Net Profit, Cash Balance, Bank Balance, Accounts Receivable, Accounts Payable, Inventory Value, Assets Value, Customers, Suppliers, Employees). "Cash Balance" and "Bank Balance" are deliberately two different figures — petty cash accounts vs. bank-linked GL accounts — rather than one combined "cash" number, matching how the chart of accounts actually separates them.
- **Charts**: Revenue Trend (line), Profit vs. Expenses (clustered bar — `BarChartWidget` renders multiple `bars` entries side-by-side automatically), Cash Flow Trend (area, via the `AreaChartWidget` that already existed but wasn't used anywhere), Revenue by Category (donut — see note below), plus an Executive Scorecard of four gauges (liquidity, net margin, ROA, debt-to-equity) using the `KpiGauge` component that already existed but also wasn't used anywhere on this page.
- **"Revenue by Department" → Revenue by Category**: the spec calls for this by department, but there's no relationship anywhere in the schema between a sale and an HR department — `employees.department` and a `sales_invoice` share no link. Revenue by *product category* is the closest real business segment the data actually supports, via a new `sales-reports/by-category` endpoint mirroring the existing `by-branch` one exactly.
- **"Sales by Branch (Interactive Map)"**: kept as the existing bar chart + table. A literal geographic map would need branch lat/long (not collected anywhere) and a mapping library dependency — flagged as a deliberate scope decision rather than silently dropped.
- **Quick Insights**: Highest/Lowest Revenue Branch, Fastest Growing Product (this month vs. last month by product), Most Profitable Category, Cash Position, Liquidity Ratio, Working Capital — all derived from data already being fetched elsewhere on the page, no new endpoints needed except the category one above.
- **Compliance — the ten items split cleanly into two real categories**: SSNIT Payable, PAYE, Output VAT, and Input VAT are **live GL account balances** (via the existing `gl_account_mappings` for `ssnit_payable`/`paye_payable`/`vat_payable`/`vat_input`) — the actual outstanding amount right now, net of payments already made, not a period filing total (that's what Tax Reports is for). WHT, VAT Withholding, Tax Clearance Certificate (Collected/Receivable), EPA Permit, and Business Operating Permit have **no data source anywhere in this system** — they're externally-issued certificates with a status and expiry date, not a number the GL can compute. New migration `037_compliance_register.sql` adds a genuine, editable `compliance_items` table for these — seeded with all six for every company, defaulting to "unknown" status until someone records the real state — surfaced on the dashboard as an inline-editable status dropdown, not a static mock.
- **Not to be confused with the pre-existing HR Compliance module** (compliance documents, company policies, incidents — `/compliance-documents`, `/company-policies`) — a completely different domain that happens to share the word "compliance". The new statutory tracker lives at `/statutory-compliance-status` specifically to avoid any collision.
- **KPI drill-down**: every KPI card is a real link to the page that explains the number (Total Revenue → Financial Statements, Accounts Payable → Purchase Invoices, Customers → Customer list, etc.) — not a static tile. Scoped to the Dashboard specifically; the same `.kpi-card` class is used as a non-clickable summary tile on 14+ other pages that this deliberately doesn't touch.
- **Date range filter**: everything period-based on the dashboard — the trend charts, top customers/products, branch and category revenue, fastest-growing product, and the point-in-time balance sheet snapshot (assets value, working capital, bank/petty cash totals) — responds to a single filter in the header (This Month / Last 3 Months / Last 6 Months / This Quarter / This Year / Custom Range), not six independent hardcoded "last 6 months" windows scattered through the page. `DateRangeFilter.jsx` exports the range-resolution logic (`resolveDateRange`) and a month-bucketing helper (`monthBucketsInRange`, capped at 12 buckets so a multi-year custom range doesn't produce an unreadable chart) as plain functions, verified directly in Node outside the component — every preset, a mid-month custom range's bucket clipping, and the 12-bucket cap were all checked against real date math, not just visually. Trend-chart subtitles and the "Fastest Growing Product" comparison (now the two most recent month-buckets *within* the selected range, rather than always literally "this month vs last month") update to match. **Deliberately not range-filtered**: receivables/payables aging and inventory valuation/low-stock stay as current-moment snapshots — these are inherently "outstanding right now" figures, not something a past date can meaningfully reconstruct without the historical snapshots this system doesn't keep. The same component was then adopted on Financial Statements (Income Statement), Sales Reports (Sales Register), Tax Reports (VAT and PAYE Summary), and Management Account Report — each previously had its own ad-hoc pair of plain `<input type="date">` fields with a manual "Run" button; all four now use the shared filter and auto-refresh when the range changes, rather than requiring an extra click. The Balance Sheet's single `asOf` date (a point in time, not a range) was deliberately left as a plain date input — a different concept the range filter isn't built for.

### How the four newest reports work

**Tax Reports** (`/reports/tax`, `accounting.tax_reports.view`): reflects Ghana's VAT Act, 2025 (Act 1151), effective 1 January 2026, which restructured VAT — the standard rate (15%), NHIL (2.5%), and GETFund Levy (2.5%) are now all calculated on the *same base*, a combined 20%, and NHIL/GETFund paid on purchases became creditable input tax for the first time (previously they weren't, and were cascaded on top of VAT rather than sharing its base, with a 1% COVID-19 Health Recovery Levy on top of that — since abolished). `LineItemsEditor.jsx`'s default tax rate for a new line was updated from the old 15%-only figure to the current 20% combined rate accordingly.
  - **VAT Summary** nets Output tax (`sales_invoices.tax_amount`) against Input tax (`purchase_invoices.tax_amount`) for a period, then splits each side into its VAT/NHIL/GETFund components by their fixed statutory ratio (15 : 2.5 : 2.5) — exact for anything taxed at the standard combined rate, and the only sound way to show the GRA-required breakdown without a schema change to store three separate tax fields per line. Includes a filing-guidance note (returns are due by the last working day of the month following the tax period, confirmed directly against `gra.gov.gh`).
  - **PAYE Summary** aggregates `payslips.income_tax` (already computed per employee per payroll run) and SSNIT employee contributions by period, with a note that they're two separate filings on two separate portals (GRA for PAYE, within 15 days of month-end; SSNIT for contributions, by the 14th).
  - **Explicitly out of scope**: Withholding Tax (WHT) on supplier/contractor payments (a materially different obligation — rates vary by payment type, e.g. 3% on goods, 7.5% on services — and isn't modeled anywhere in the schema today; adding it would mean new fields on purchase invoices/payments, not just a report change) and Corporate Income Tax quarterly installments. Noted here rather than silently left unaddressed, same as the IFRS Statement of Cash Flows / Statement of Changes in Equity note above.

**HR Report** (`/reports/hr`, `hr.reports.view`) and **Departmental Reports** (`/reports/departmental`, same permission): pull together HR data that used to only exist as tabs buried inside other pages (HR & Payroll, Learning & Development, HR Compliance) — headcount, payroll cost trend, training costs, and attendance, either per-employee (HR Report) or grouped by department (Departmental Reports, plus a new `attendance-by-department` endpoint alongside the existing per-employee one). `employees.department` is a free-text field, not a separate table, so both reports bucket anything blank under "Unassigned" rather than dropping those employees.

**Management Account Report** (`/reports/management-accounts`, `accounting.management_reports.view`): restructured to follow the standard "comparative management accounts" format (Current Period / Previous Year / Change) rather than a single-period snapshot — matching the professional template this was built against. An Executive Summary table up top (Revenue, Gross Profit, Operating Profit, Net Profit, Cash Balance vs the same period last year), a Financial Highlights KPI grid with a trend chip under each figure (colored, no motion — consistent with the rest of the app since decorative animation was deliberately removed elsewhere), and both the Income Statement and Statement of Financial Position sections now render Current + Prior Year side by side. The prior period is always the *literal same date range one year back* (`shiftYearBack()`), computed by calling the exact same `accountBalancesAsOf`/`movementBetween` helpers a second time — never a second parallel calculation that could drift from the current-period figures or the dedicated Financial Statements page.

A full management accounts pack in the template this was built against has 20 sections — Budget vs Actual, Departmental Performance, AR/AP Analysis, Inventory Analysis, Fixed Assets Schedule, Bank Reconciliation, Tax computation, and more. Rather than rebuild each of those a second time on this page, a "Rest of the report pack" section links straight to wherever that section already lives as its own dedicated page (Budgets, Departmental Reports, Sales Reports, Inventory Reports, Assets, Banking, Tax Reports) — each link gated by the same permission its destination route already requires, so nothing appears as a dead link for a user who can't access it.

- **Bug found and fixed while building this**: `movementBetween()` (used by the Income Statement and this report for period-over-period figures) had a real, pre-existing date-filtering bug — the date range was applied inside a `LEFT JOIN`'s `ON` clause against `journal_entries`, but the actual `SUM()` was over `journal_entry_lines` joined *unconditionally* in an earlier join, so the date filter never actually restricted anything; every call silently returned all-time totals regardless of the `from`/`to` requested. This was invisible until a query used a period that genuinely excluded some existing data (like a prior-year comparison against a database with no data before the current year) — every previous test in this app had used ranges that happened to include all the data. Fixed to match `accountBalancesAsOf`'s already-correct pattern (pre-aggregate in a subquery joined to `journal_entries` first, *then* left-join that to the chart of accounts) — verified directly: a 2025 query against data that only exists in 2026 now correctly returns 0, and the 2026 figures are unaffected.

### How procurement works

Procurement is the buy-side mirror of Sales, and the pipeline is deliberately loose: a purchase order can be raised standalone or from an approved requisition (optionally via an RFQ and supplier quotation); goods can be received in full or in part; a purchase invoice can reference a PO or stand alone; and supplier payments can be split across several bills or left partially unallocated. Each PO line independently tracks `received_quantity` and `billed_quantity`, so partial receipts and partial billing against the same order both work.

- **Goods receipt → stock-in**: recording a goods received note (GRN) calls the same `stockService.receiveStock` the rest of the system uses, so received goods land in the Module 05 inventory ledger with batch number and expiry captured for batch-tracked products, and the PO status advances to `partially_received` / `received` automatically.
- **GRNI clearing**: a GRN now posts Dr Inventory / Cr `2050 GRNI Clearing` at receipt time, so the GL inventory balance matches the physical stock ledger immediately — it no longer waits for the supplier invoice. When the purchase invoice is later entered, PO-linked lines (the normal case — goods already received via GRN) clear GRNI instead of re-debiting Inventory; a fully standalone invoice line (no PO reference, i.e. never received through the GRN flow) still debits Inventory directly, as before. A purchase return posts a reversing entry — Dr Accounts Payable / Cr Inventory / Cr Input VAT (if any) — mirroring the original purchase invoice. Supplier payments still post Dr Accounts Payable / Cr Cash. All of this is gated by the same `hasAllMappings` safeguard as Sales — if a company hasn't set up its accounts, procurement still works, it just doesn't post. Input VAT goes to a dedicated `1300 Input VAT Recoverable` asset account so it can be netted against output VAT on a GRA return.
- Suppliers have a `credit_limit` (0 = cash-only), mirroring the customer side. Creating a purchase invoice checks the supplier's total outstanding (unpaid, non-void invoices) against it and returns a `creditWarning` if over limit — informational only, it does not block the invoice.

### How multi-currency works

`026_multi_currency.sql` activates the `currencies` and `exchange_rates` tables that had been scaffolded (unused) since `001_init_schema.sql`, and adds `currency` + `exchange_rate` columns to every sales and procurement document: quotations, sales orders, sales invoices, sales returns, customer payments, purchase orders, GRNs, purchase invoices, purchase returns, and supplier payments.

- **Design principle**: a document's subtotal/tax/total stay in its **own** currency — what the customer or supplier actually sees. `exchange_rate` is the rate to the company's `base_currency` at the time the document was created (or settled, for payments). Every GL posting converts to base currency using that stored rate *before* calling `postJournalEntry` — the ledger itself never stores foreign amounts in `debit`/`credit`, so the trial balance, financial statements, and every existing report keep working completely unmodified. `journal_entries` also gained an audit-only `(currency, exchange_rate, foreign_total)` trio — nothing reads these for calculations, they just answer "what did this base-currency entry equate to in the original currency."
- **Rate resolution**: `currencyService.getRate()` checks for a direct rate (e.g. USD → GHS) as of the document's date, then falls back to the inverse of the reverse-direction rate if that's what's on file — you only need to enter a pair in one direction. A document's currency defaults to the customer's/supplier's own default (`customers.currency` / `suppliers.currency`, nullable = company base currency), and its rate defaults to the latest one on file, though both can be overridden per document.
- **Rate inheritance through a document chain**: converting a quotation → sales order → invoice carries the *exact same* currency and rate forward at each step, rather than re-resolving against "today's" rate every time — a confirmed order shouldn't reprice itself. The same applies on the buy side: PO → GRN → purchase invoice.
- **Inventory valuation is the one deliberate exception**: `stock_batches`/`stock_levels.average_cost` are *always* in base currency — it's one shared costing pool used for COGS and reporting regardless of which currency any given purchase happened in. A GRN converts the received unit cost to base currency (using the PO's own rate) before it ever touches the stock ledger, not at GL-posting time; `grn_lines.unit_cost` still records the original foreign-currency cost for document display.
- **Realized FX gain/loss**: this is the part that only shows up once money actually changes hands at a different rate than the original document was booked at. A customer receipt (or supplier payment) clears Accounts Receivable/Payable at each invoice's *own* rate (not today's), while Cash moves at today's rate — the difference is posted to a new `4930 Foreign Exchange Gain` or `6930 Foreign Exchange Loss` account (mirroring the existing `asset_disposal_gain`/`asset_disposal_loss` pattern: one account per direction, not a single netted account). Applying previously-unallocated funds to an invoice later can realize FX gain/loss too, even with no new cash movement, if the payment's rate differs from the invoice's rate.
- **A return is an undo, not a new FX event**: a sales or purchase return against a specific invoice reverses it at that invoice's *exact* original rate — there's no cash movement to realize a gain or loss against, so using any other rate would just introduce a stray difference. A standalone return (no invoice reference) falls back to the customer's/supplier's default currency and today's rate, like any new document.
- **Same-currency allocation only**: a payment can only be allocated against invoices in its own currency — settling a foreign-currency invoice with a different-currency receipt would need its own conversion step, which isn't modeled here. Record two separate payments instead.
- **Per-company enabled currencies**: `company_currencies` lets each company enable/disable which currencies its own users can pick from documents, without one company's settings affecting any other (the global `currencies` table is shared reference data, similar to how country/region codes are shared).
- **Known limitation**: only the backend and an Accounting → Currencies & Exchange Rates settings page are built. The currency/rate selector on quotation, sales order, invoice, and payment creation forms (both sales and procurement) still needs the UI added — the API already accepts and defaults `currency`/`exchangeRate` on every one of those endpoints, so a document created without passing them just uses the customer's/supplier's default currency and the latest rate on file.

### How recurring invoices work

A `recurring_invoice_templates` row holds a customer, a fixed set of line items, and a schedule (`frequency` + `next_run_date`, optionally an `end_date`); `recurring_invoice_lines` holds the repeated line items. Nothing about invoice generation itself is reimplemented — `invoiceController.js`'s `createInvoice` was split into a thin route handler plus an exported `generateInvoice(client, {...})` function, and `recurringInvoiceService.js` calls that exact same function, so a generated invoice gets identical GL posting, currency handling, and credit-limit checking to one created by hand.

- **Background scheduler, not a cron job**: `startRecurringInvoiceScheduler()` (called once from `server.js` on boot) runs an in-process check 10 seconds after startup and then every hour via `setInterval`, looking for every `active` template across every company where `next_run_date <= CURRENT_DATE`. Each due template runs in its own transaction, so one template's failure (e.g. a deleted product) can't roll back another's — a failure is logged and skipped rather than crashing the batch.
- **`sales_invoices.recurring_template_id`** traces which invoice came from which template (and lets the template detail page show its full generation history), rather than trying to infer it from dates.
- **Manual "Run now"**: `POST /recurring-invoices/:id/run-now` runs the exact same generation path immediately, for generating a cycle's invoice a few days early. Only `active` templates can be run this way.
- **Status lifecycle**: `active` → `paused` (skipped by the scheduler, resumable) → `ended` (terminal; also set automatically once a generated invoice's next cycle would fall after `end_date`).
- **Notification**: generating an invoice notifies everyone holding `sales.recurring_invoices.manage`, reusing `notificationService.js`'s existing `notifyUsersWithPermission`, the same pattern as requisition approvals.

### How report export (Excel/PDF/Word) works

`exportService.js` is a small, Express-agnostic engine that turns report data into a real file — no separate export routes or duplicated queries. Any report endpoint that supports it just checks `req.query.format` before its normal `res.json(...)` and, if present, calls `sendExport(res, format, filenameBase, data)` instead with the exact same data it already computed.

- **Two shapes cover every report**: a flat **table** (`{ title, subtitle?, columns: [{ key, label, align?, format?, width? }], rows }`) for register/listing-style reports, and a sectioned **statement** (`{ title, subtitle?, sections: [{ title, lines: [{label, amount}], total? }], grandTotal? }`) for the income statement and balance sheet. `format` on a column is `'currency' | 'number' | 'date'` and controls both the on-screen text formatting (PDF/Word) and the underlying cell type/number format (Excel) — dates and numbers land in Excel as real dates/numbers, not text, so totals and sorting work in the downloaded file.
- **Libraries**: `exceljs` for `.xlsx` (with actual cell styling — bold headers, brand-green header fill, currency/date number formats — not just plain values), `pdfkit` for `.pdf` (hand-laid-out tables with header repetition across page breaks, landscape for wide tables), and `docx` for `.docx` (real Word tables/headings, not an HTML-to-Word hack).
- **Known dependency trade-off**: `exceljs` pulls in `archiver` (for the `.xlsx` zip container), which has a transitive `glob`/`minimatch`/`brace-expansion` chain with a known high-severity advisory and no clean upstream fix (`npm audit fix --force` only offers a downgrade to a much older `exceljs` major version). In this app's actual usage, `archiver` only ever zips worksheets built from our own DB-queried data — never a user-supplied file path or glob pattern — so the realistic exploitability here is low, but it's a real, open item worth knowing about rather than a silently-accepted one.
- **Frontend**: `ExportMenu.jsx` is a single shared dropdown (Excel/PDF/Word) that calls the report's own existing endpoint with `{ ...params, format }` and `responseType: 'blob'`, then triggers a browser download — there's no separate "export data" concept on the frontend to keep in sync with a report's filters. Wired into Income Statement, Balance Sheet, Receivables Aging, Sales Register, Low Stock, Stock Valuation, and Stock Expiry. Sales Summary and Financial Ratios are chart/gauge-heavy views without a natural single-table shape and aren't wired up (no backend support either).

### How the Communication Centre works

Three independent pieces, deliberately kept separate rather than forced into one feed:

- **Notifications**: a personal, per-user feed (bell icon in the topbar, polled every 30s, plus a full view at `/communications`). Nothing needs a special permission to read or mark its own notifications — it's scoped by `user_id` the same way your email inbox is yours regardless of role. Two things write to it today: requisition approval events (submitting one notifies everyone holding `procurement.requisitions.manage`; approving/rejecting one notifies the original requester) and announcements (see below). `notificationService.js` exposes `notifyUser` / `notifyUsersWithPermission` / `notifyAllActiveUsers` so future modules can hook in the same way without duplicating the targeting logic.
- **Alerts**: overdue receivables, overdue payables, and low stock. These are deliberately *not* persisted rows — they're ongoing facts, not one-time events, so `GET /notifications/alerts` computes them live against current data every time it's called (the low-stock query is kept identical to the one in `inventoryReportController`). Each section only appears if the requesting user already holds the permission that gates the underlying data (`sales.invoices.manage`, `procurement.invoices.manage`, `inventory.reports.view`), so this never surfaces figures a person couldn't otherwise see.
- **Communication log**: a call/email/meeting/note history attached to a specific customer or supplier, shown at the bottom of that record's ledger page. Logging an entry reuses the same permission that already gates editing that customer/supplier (`sales.customers.manage` / `procurement.suppliers.manage`) rather than a new permission.
- **Announcements**: a company noticeboard (`communications.announcements.manage` to post; anyone can read). Posting one writes a canonical `announcements` row and fans out a notification to every other active user in the company in the same transaction.

### How HR & Payroll works

Employees are first-class records in the `employees` table, deliberately separate from `users`. Not every employee needs a system login, and not every system user is on payroll. An employee can optionally be linked to a user account via the `user_id` foreign key if they do need system access.

- **Employee records**: each employee carries a job title, department, employment type (full-time / part-time / contract), employment status (active / on_leave / terminated), manager reference, hire date, basic salary, allowances, bank details, SSNIT number, and TIN. Terminating an employee is a dedicated endpoint (`POST /employees/:id/terminate`) that sets their status and termination date atomically.
- **Leave management**: company-configurable leave types (Annual, Sick, Maternity, etc.) with a per-year entitlement. Leave requests go through a submit → approve/reject workflow. When a leave request covering today's date is approved, the employee's status automatically flips to `on_leave` so payroll and rostering can see it.
- **Payroll runs**: one run per company per month (enforced by a unique constraint). The lifecycle is `draft` → `processed` → `paid`. Creating a run is a lightweight placeholder; processing it iterates every active/on-leave employee and generates a payslip with: gross pay (basic + allowances), SSNIT employee deduction (5.5% of basic salary — Ghana tier-1), PAYE income tax (computed on chargeable income using GRA cumulative bands), other deductions (placeholder, currently 0), and net pay. After processing, the run can be marked `paid`. Re-processing a run regenerates all payslips (the `ON CONFLICT DO NOTHING` guard prevents duplicate payslips for the same employee in the same run).
- **Configurable statutory rates**: SSNIT rates and PAYE bands are stored per company in `payroll_settings` and `paye_tax_bands`, not hardcoded, and are read fresh at processing time. **HR & Payroll → Statutory Settings** exposes the employee rate, employer rate, annual insurable ceiling, whether allowances count toward chargeable income, and the full band table. Band edits are validated before they are saved — bands must start at 0, be contiguous, and have exactly one open-ended top band — so it isn't possible to save a schedule that leaves a slice of income untaxed or taxes it twice. Ghana's current rates ship as defaults, but when the GRA revises the schedule you update it in the UI rather than waiting on a code change.
- **The employer's SSNIT share**: the employer contribution (13% of basic by default) is modelled as a business cost, not an employee deduction. It never reduces take-home pay, but it is expensed to *SSNIT Employer Contribution* and credited to *SSNIT Payable* alongside the employee's share, so the full amount owed to SSNIT appears on the balance sheet.
- **GL auto-posting**: processing a run posts a balanced journal entry dated the last day of the payroll month:

  | | Debit | Credit |
  |---|---|---|
  | Salaries & Wages | gross | |
  | SSNIT Employer Contribution | employer share | |
  | PAYE Payable | | total PAYE |
  | SSNIT Payable | | employee + employer share |
  | Net Salaries Payable | | net pay |
  | Staff Deductions Payable | | other deductions |

  This balances because gross = net + PAYE + employee SSNIT + other deductions, so the debits (gross + employer SSNIT) always equal the credits. Marking a run `paid` posts the settlement — Dr Net Salaries Payable / Cr Cash — which clears the salaries liability while PAYE and SSNIT stay on the books until they are remitted to the GRA and SSNIT. Both postings are gated by the same `hasAllMappings` check used by Sales and Procurement, so payroll still runs for a company that hasn't set up its chart of accounts; it just doesn't post.
- **Permissions**: six permission codes — `hr.employees.manage`, `hr.leave.manage`, `hr.leave.approve`, `hr.payroll.manage`, `hr.payroll.view`, and `hr.settings.manage` (editing statutory rates) — are seeded by the migrations and granted to every existing Super Admin role automatically.

### How asset management works

Asset categories carry their own GL account wiring rather than relying on global mappings — each category names the asset account, the accumulated depreciation account, and the depreciation expense account it posts to. That means a company can keep vehicles, IT equipment, and buildings in separate accounts without any code changes.

- **Depreciation runs**: a periodic run (`POST /fixed-assets/depreciation-run` with a period start and end) computes the charge for every eligible asset and posts one journal entry — Dr Depreciation Expense / Cr Accumulated Depreciation. Straight-line and reducing-balance are both supported, driven by the asset's useful life and residual value.
- **Revaluation, impairment, disposal**: each is a distinct endpoint with its own posting. Gains and losses route to dedicated accounts (Gain/Loss on Disposal, Impairment Loss, Reversal of Impairment, Revaluation Surplus) so the P&L and equity effects stay separable.
- **Note on the chart of accounts**: the base chart shipped `1510 Accumulated Depreciation` but no matching expense account, so `012_asset_management.sql` adds `6050 Depreciation Expense` and new companies get it seeded at registration. Without it, categories had to post the charge to Miscellaneous Expense.

### How CRM works

The CRM module fills the gap between "stranger" and "customer" that the Sales module doesn't cover. Leads are the pre-customer pipeline; contacts are named people attached to leads or customers; activities are a shared communication/follow-up log.

- **Leads**: each lead has a name, optional company name, email, phone, source (referral, walk-in, website, etc.), a six-stage pipeline (new → contacted → qualified → proposal → won → lost), estimated value, expected close date, and an assigned owner (a system user). Leads that progress to "won" can be converted to a real customer via `POST /leads/:id/convert`, which atomically creates a `customers` row, migrates all the lead's contacts to the customer, and links the two records so the lead's detail view shows the conversion.
- **Contacts**: a contact belongs to either a customer or a lead (enforced by a CHECK constraint). Contacts carry first/last name, job title, email, phone, and a primary flag. When a lead converts, its contacts are reassigned to the new customer automatically.
- **Activities**: a shared log of calls, emails, meetings, notes, and follow-up tasks attached to either a customer or a lead. Tasks have a `due_date` and an `is_done` flag. The background notification scanner (see below) picks up overdue follow-up tasks and surfaces them as notifications automatically.
- **Permissions**: three new permission codes — `crm.leads.manage`, `crm.contacts.manage`, `crm.activities.manage` — are seeded by the migration and granted to every existing Super Admin role automatically.

### How the background notification scanner works

Alongside the CRM migration, a background scanner was added to `notificationService.js`. It runs every 15 minutes (starting 5 seconds after boot) and scans every active company for four kinds of standing issues:

1. **Low stock** — products at or below their reorder level in any warehouse
2. **Overdue sales invoices** — customer invoices past their due date with a balance outstanding
3. **Overdue purchase invoices** — supplier bills past their due date with a balance owed
4. **CRM follow-ups overdue** — activities with a `due_date` in the past that haven't been marked `is_done`

Each issue type uses a stable `dedupe_key` so the scanner can upsert (insert-or-update) notifications without creating duplicates, and auto-resolve them when the underlying issue clears. Scanner notifications are company-scoped (`user_id IS NULL`) — they appear in the Communication Centre's alerts section — while personal notifications (requisition approvals, announcements) remain user-scoped as before. The migration extends the `notifications` table with `severity`, `message`, `related_entity_type`, `related_entity_id`, `dedupe_key`, and `resolved_at` columns, all nullable so nothing breaks for existing rows.

## Prerequisites

## Setup

### 1. Database

Create a database and apply the schema:

```bash
createdb bizness_os
cd server
cp .env.example .env
```

Edit `server/.env` and set `DATABASE_URL` to point at your PostgreSQL instance, e.g.:

```
DATABASE_URL=postgres://postgres:yourpassword@localhost:5432/bizness_os
```

Also set real random strings for `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` (don't use the placeholders in production).

Run the migration:

```bash
npm install
npm run migrate
```

This creates all tables and seeds the base permission catalog + currency list.

### 2. Backend

```bash
cd server
npm run dev      # starts on http://localhost:5000 with auto-reload
```

Health check: `curl http://localhost:5000/health`

### 3. Frontend

```bash
cd client
cp .env.example .env    # VITE_API_URL defaults to http://localhost:5000/api
npm install
npm run dev              # starts on http://localhost:5173
```

Open http://localhost:5173, click **Create an account**, and register your company. That first user becomes the Super Admin with every permission.

## How permissions work

- Permissions are granular codes like `system.users.manage`, `system.roles.manage`, `system.company.manage`, `system.financial_periods.manage`, `system.audit.view`, `dashboard.executive.view`.
- Roles bundle permissions. Users get one or more roles.
- Every company automatically gets a system-protected **Super Admin** role with all permissions on registration — this role can't be edited or deleted, so there's always at least one account that can recover access.
- The API enforces permissions server-side via the `requirePermission()` middleware — the frontend sidebar just hides links the user can't use, it isn't the security boundary.

## What's next

The database schema and route/controller structure are intentionally modular — each future module (Inventory, Sales, Payroll, Accounting, etc.) follows the same pattern:
1. Add tables to a new migration file (`002_inventory.sql`, etc.)
2. Add a `permissions` catalog entry for the new module
3. Add a controller + route file
4. Add a page + sidebar entry on the frontend

Suggested build order for the remaining modules: **Supplier Management** → **Asset Management** → **Approval Workflows**.
